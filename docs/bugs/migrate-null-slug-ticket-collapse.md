## Observed

Running the setup-workflow migration on a schema 3 repo with a live
`docs/tasks/maps/<map>/tickets/<slug>/ticket.md` subtree moves every ticket to
the single file `docs/tasks/<effort>/tickets/null/ticket.md`. Each write
overwrites the previous ticket. In the reporting repo (pi-reins, downstream),
12 tickets collapsed and only the last (`task-lifecycle`) survived on disk.
The printed MigrateReport shows the symptom: the same destination line
repeated once per ticket.

The data was recovered afterwards from git; the originals were byte-identical
restores. Two `submit_feedback` entries (kind `bad`, kind `friction`) were
recorded in the reporting repo.

This repo's own tree has no live `maps/<map>/tickets/` subtrees, which is why
our own migration never exercised the path.

## Expected

Each ticket moves to `docs/tasks/<effort>/tickets/<slug>/ticket.md`, with one
directory per ticket, no overwrites, and a needs-human report when a slug
cannot be derived.

## Reproduction

1. Take a schema 3 repo with a live map holding tickets (the reporting repo
   at commit c5441ea, branch main, has
   `docs/tasks/maps/phase1-execution-contract/tickets/*/ticket.md`), or build
   a synthetic fixture with two tickets `a` and `b` under
   `docs/tasks/maps/<map>/tickets/`.
2. `git checkout -b migrate/schema-3-to-4`
3. Run `node skills/engineering/setup-workflow/scripts/migrate.mjs` with that
   repo as root.
4. Observe: both tickets land at `docs/tasks/<effort>/tickets/null/ticket.md`
   and only the last one survives.

## Suspected area

`src/core/migrate.ts`: `vintageLocation`, `v4Home`, and the `plan.writes`
staging in `reorganize`.

## Root cause

Three layered defects:

1. `src/core/migrate.ts:521-522`: the live `maps/<map>/...` branch of
   `vintageLocation` returns `slug: null` and never extracts the ticket or
   task directory name from `rest[3]` when the subtree is a `tickets/` or
   `tasks/` container. The archive branch (around line 528) already derives
   the slug from `rest[3]`; the live-maps branch does not.
2. `src/core/migrate.ts:1008`: `v4Home` for tasks and tickets interpolates the
   slug into the destination template without a null guard, while `effort`
   directly above IS guarded and bails out. In a JS template literal `${null}`
   becomes the literal text `null`, so the destination is
   `tickets/null/ticket.md` for every ticket.
3. `src/core/migrate.ts:855`: `plan.writes` is a Map keyed by destination
   path; `plan.writes.set(dest, content)` from 12 different sources with the
   same destination silently overwrites. No collision detection exists, and
   the YAML round-trip verification validates each write in isolation, so the
   corruption-safety guarantee does not catch the collapse.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** The schema 3 to 4 migration silently destroys all but the last
ticket of a live map subtree by collapsing them onto one `tickets/null/`
destination; fix all three layers and add regression coverage.

**Current behavior:**
For a ticket or task living under a live `maps/<map>/tickets/<slug>/` (or
`tasks/<slug>/`) subtree, the location classifier returns a null slug, the
v4 home computation interpolates that null into the destination path (JS
template literals stringify `null`), and the plan staging keyed by
destination silently overwrites earlier writes with later ones. The result:
every ticket of the subtree lands at one shared `tickets/null/ticket.md`
destination, only the last write survives, the YAML round-trip verification
passes (each write is valid in isolation), and the printed report repeats the
same destination line once per ticket.

**Desired behavior:**
- A ticket or task directory under a live `maps/<map>/tickets/` or
  `maps/<map>/tasks/` subtree contributes its directory name as the slug,
  mirroring how the archive branch already handles the same shape.
- When a task or ticket has no derivable slug, the destination computation
  bails out with a needs-human item and leaves the artifact in place, exactly
  as the existing empty-effort guard does. A destination path never contains a
  literal `null` segment.
- When two different sources would stage a write to the same destination,
  the plan staging detects the collision and reports it as a needs-human item
  instead of overwriting. Any future collapse becomes a reported failure,
  not silent data loss.

**Key interfaces:**
- `vintageLocation(path)` (returns `{ archived, effort, slug }`): the live
  `maps/<map>/...` branch must return the segment after a `tickets` or
  `tasks` container as the slug when it exists, mirroring the archive
  branch's already-v4 shape.
- `v4Home(...)` (returns the destination path or null): the task and ticket
  branch must guard the slug the same way the effort is guarded today; a
  null slug for a task or ticket pushes a needs-human item and returns null
  (skip the artifact), never string interpolation.
- The plan's `writes` staging (destination path to content): must detect that
  a destination is already claimed by a different source and convert the
  collision into a needs-human item naming both sources, rather than a silent
  overwrite. The existing `HumanItem` shape is the reporting vehicle.
- The MigrateReport's needs-human section surfaces these items to the
  operator.

**Acceptance criteria:**
- [x] A schema 3 fixture with `maps/<map>/tickets/a/ticket.md` and
      `maps/<map>/tickets/b/ticket.md` migrates each ticket to
      `<effort>/tickets/a/ticket.md` and `<effort>/tickets/b/ticket.md`
      respectively, with both bodies preserved verbatim.
- [x] No destination path produced by the migration contains a literal
      `null` path segment; a task or ticket whose slug cannot be derived
      produces a needs-human item and is left in place.
- [x] Staging two different sources to the same destination surfaces a
      needs-human item naming both sources; neither write silently wins.
- [x] The printed MigrateReport no longer repeats one destination line per

- [x] The regression test above is red on the unfixed code and green after

- [x] The migration's corruption-safety story states how destination

**Out of scope:**
- Recovering the lost tickets in the reporting repo (already restored from

- Changing the archive branch's slug derivation (already correct).
- Redesigning the MigrateReport output format beyond the new needs-human

## Fix summary

Fixed in three layers, one per diagnosed defect:

1. `vintageLocation` derives the slug for both map-subtree branches: when
   the segment after the map is a `tickets/` or `tasks/` container, the
   following segment is the slug, mirroring the archive branch. This covers
   live `maps/<map>/...` and archived `maps/archive/<map>/...` subtrees
   alike; the archived-map branch carried the same one-line defect (never
   exercised by this repo's own tree, whose archived maps hold no
   tickets), so both were fixed as one class.
2. `v4Home` guards the slug for tasks and tickets the way effort is
   guarded: a null slug pushes a `no-slug` needs-human item and returns
   null, so the artifact is left in place. No destination ever contains a
   literal `null` segment.
3. Every staging site (primary artifacts, aux backfill, anchor moves,
   state, index, changelog, out-of-scope index, vendored pointers) claims
   its destination through `claimDest` before staging: the first claim
   stands, and a later, different source becomes a
   `destination-collision` needs-human item naming both sources while the
   later artifact is left in place. This is the backstop that converts any
   future silent collapse into a reported failure.

An aux file beside a map-subtree ticket follows its ticket again (the
placement key is now the ticket's slug, not the shared empty key that
produced `tickets//`-style destinations).

Regression tests (red on the unfixed code): the two-ticket live-map
fixture, an aux file following its ticket, the archived-map subtree, the
slugless ticket (reported, left in place, no `null` segment anywhere), a
deliberate two-source collision (first claim stands, later source left in
place, re-reported on re-run), and re-run idempotence. Full suite 740/740,
typecheck clean. Verified end-to-end through the migration CLI on the
triage reproduction fixture: both tickets arrive at their own directories
and the report shows one destination line per ticket.
