## Decision to settle

The exact content of a profile, and the per-phase matrix for the two profiles
this effort ships, `default` and `flat`. This is the heart of the effort: the
skills stay free of git instructions only if the profile says precisely what
each phase must do.

## What a profile carries (settled in `non-negotiables`)

For each workflow phase (intake, wayfinder, to-spec, to-tickets,
implement-ticket, finalize-effort), all optional:

- a branch name template (the branch the phase must be on, and the branch the
  phase may create);
- opening instructions, injected at `tw_open`;
- closing instructions, injected at `tw_close`;
- a closing branch gate.

For the implementation sub-agents (tdd-worker, land-worker, deviation-reporter,
slice-verifier, implement-preconditions), only a branch gate template.

## Choices still open

1. **What `default` means.** The operator's model: a dedicated feature branch
   per effort, created by `implement-ticket` as its first action, with each
   ticket landing back onto it. Whether `default` also keeps today's per-ticket
   landing branch (`task/<slug>`) and working branch (`ticket/<slug>`), or
   merges a finished ticket straight onto the feature branch, is open.
2. **What `flat` means.** The operator's reason for wanting it: work repos
   where the branching workflow is not theirs to choose. Candidates: no
   per-ticket branches at all, work committed directly on the integration
   branch; or per-ticket branches with a different naming convention only.
3. **The placeholder vocabulary** in templates, for example `{effort}`,
   `{ticket}`, and whether the merge flag and push policy are per profile or
   only in the settings block.
4. **How a custom profile is added later as data**, for example
   `taskWorkflow.git.profiles.<name>` in settings merged over the profile it
   extends. The mechanism must not hardcode two profile names in code paths.
5. **Where the bundled profiles live**: shipped data files in the package, or
   constants in the extension.

## Recommended starting answer

`default` = feature branch `effort/{effort}` created at implementation start;
per-ticket landing branch `task/{ticket}` off the feature branch; working branch
`ticket/{ticket}` off the landing branch; land-worker merges the working branch
into the landing branch; close-out merges the landing branch into the feature
branch. `flat` = no landing branches; `ticket/{ticket}` off the integration
branch, merged straight back into it. Templates carry `{effort}` and `{ticket}`.
Bundled profiles ship as data files, and settings may override any single key,
which is also how a custom profile arrives later.

## Downstream

The profile matrix decides the guards, so `feature-branch-rejoin` and the spec's
gate table wait on this. The spec's settings schema also follows from it.

## Notes

## Round 2 settled (operator's answers)

- **`flat` gates nothing.** No branch templates, no instructions, no guards:
  "flat should just become no restrictions, just do whatever". It is for repos
  with nothing going on, or where no fixed workflow is allowed, and the operator
  drives git by hand there.
- **The instruction fields stay.** They are the extensibility mechanism for later
  custom profiles. Both bundled profiles ship them empty, and the bundled branch
  step is generated by the extension from the template rather than written as
  prose.
- **Trunk setting shape accepted**, as one object with defaults: `develop` false,
  `main` named `main`, `develop` named `develop`. The resolved trunk is the
  `develop` name when `develop` is true, otherwise the `main` name.
- **Profiles ship as flat JSON files in the package**, loaded by the extension.
  No settings-level override of profile content in this effort: "we don't do
  overrides from the settings yet, that may come later". The only related setting
  is which profile to use. Custom profiles are not supported yet either.

## Final shape recorded by this task

Settings (`taskWorkflow.git`): `profile` (`"default"` or `"flat"`) and `trunk`
(`{ develop, main, develop }` with defaults). Everything else lives in the
profile JSON: per-phase branch template, opening instructions, closing
instructions, closing branch gate; per implementation sub-agent branch gate
template; merge flag; push policy.

## Round 1 settled (operator's answers)

**Branch levels: three, no landing branches.**

- The trunk: one branch, `develop` when the repo has one, otherwise `main`.
- Effort branches: one per effort.
- Ticket branches: one per ticket.

The operator dropped the ticket landing branch (`task/<slug>`) outright: "no task
landing branches or whatever, just main/develop, effort and ticket". `land-worker`
merges a finished ticket branch into the effort branch and deletes it.

**A fifth setting exists:** whether the repo has separate `main` and `develop`
branches, plus custom names for them. So the configurable areas are the trunk
configuration, the effort pattern, the ticket pattern, the merge flag, and the
push policy.

**No branch restriction on the planning phases.** The operator removed the
`main` rows for intake, wayfinder, to-spec, and to-tickets: "I would just not put
any restriction on that". A guard applies only where a profile names a branch.

**Guarded phases:** `implement-ticket` and `finalize-effort`, both on the effort
branch.

**Sub-agent matrix, uniform:** all five implementation sub-agents
(`implement-preconditions`, `tdd-worker`, `slice-verifier`, `deviation-reporter`,
`land-worker`) must be on the ticket branch at spawn. "The subagent matrix is
literally just be on the ticket branch, that's it." The guard covers all five.

## Earlier round in this task, superseded

The first round proposed planning phases on `main` and a two-level ticket branch
model with a landing branch. Both were rejected: planning carries no restriction,
and the landing level is gone.
