## Settled architecture (from the specification)

- **Gated skill set is a static manifest of 10 names**: task-workflow-overview, setup-workflow, intake, wayfinder, to-spec, to-tickets, implement-ticket, finalize-effort, task-workflow-doctor, workflow-failure. The manifest (`GATED_SKILL_NAMES`) lives directly above the skill registry it mirrors. Three of the ten names (task-workflow-overview, task-workflow-doctor, workflow-failure) own no toolset and therefore have no registry entry, so the manifest mirrors the registry's workflow entries plus those three. It replaces `loadGatedSkillNames()`, whose all-basenames derivation and stale hardcoded fallback both disappear. The generic skills' one-line workflow-failure header rule becomes accepted inert prose in gated repos; no header rewording anywhere.
- **Tool registration splits by the gate**: in a gated repo, only `tw_open`, `tw_close`, and `tw_feedback` register from the `tw_*` set, plus `notify_user` (which moved out of the ungated-only branch; it is generic and reads only the user's ntfy config). Every other `tw_*` tool, including all writers and the dispatcher companions `tw_next` and `tw_request_tool`, stays unregistered. In an ungated repo the full set registers as today.
- **skill-creator's bundled tools also register in gated repos**: `skill_validate`, `skill_scaffold`, and `skill_discover` are generic, workflow-independent, and the only tools a kept skill's disclosure activates. They register as today (inactive), so the restricted `tw_open` can disclose skill-creator's toolset to the model in a gated repo. Without this, the disclosure path would find nothing to activate, which is exactly the "kept in name only" failure the non-negotiable facts forbid.
- **`tw_open` is restricted in gated repos to non-gated registry entries**: its `skill` parameter's offered list narrows to the registry entries `openableWhenGated()` keeps (registry minus the gated manifest, currently exactly `skill-creator`); asking for any manifest name is refused at runtime with the opener's refused-outcome shape and a best-effort notify in the message family and warning level of the existing skill-invocation gate. The narrowing is the parameter description's enumerated list, not a parameter enum: `skill` stays `Type.String` because a provider-validated union short-circuits the opener's own refusals (the repo's testing record documents the bare union shipping broken on DeepSeek), so the description list keeps the model from seeing a hopeless value while the runtime refusal enforces the surface. The refusal is the first check in `tw_open`'s execute handler, ahead of `validateOpenArgs` (which throws and cannot carry the refused-outcome shape of `reason` and `legal_next`), so it covers the whole ten-name manifest, including the three names with no registry entry, matching the `/skill:` invocation block. `legal_next` derives from `openableWhenGated()`, not from a pinned string. The gate state reaches the restriction through `createTools(gated)`, fed `gate.active` by the factory; the refusal's notify is best-effort through the new optional `ToolContext.notify(message, level)`, wired from the session UI in the shared registerTool execute wrapper, and the refused outcome always returns. `tw_close` needs no restriction (closing what does not open is already a handled refusal). No `skill_*` tool becomes default-active; they activate through the disclosure exactly as today. The disclosure's open-set derivation is proven sound by a test when only `skill-creator`'s toolset can ever be active.
- **The write lockdown registers on 'workflow enabled', not 'gate inactive'**: the guard hooks used to register inside the gate-inactive branch, which coincided with the workflow being on. Once passive tools register in gated repos the two conditions diverge, so the guard has its own explicit condition tied to the workflow being enabled in that repo (the module-private `workflowEnabled(gate)` predicate, which also keys the declared-set replay). Refusal texts and exemptions are unchanged.
- **Session-start behavior in gated repos**: the skill-strip and `/skill:`-invocation block hooks keep firing, gated-only (strips now cover only the manifest's 10). The gated branch's session-start early return is gone, so the gate diagnostics notify in both gate states. The active-tool-set replay from transcript (`restoreDeclaredSetFromTranscript`) is workflow-bound and stays ungated-only. The peer-extension checks (pi-subagents, pi-telemetry present) fire in both gate states, since the package still depends on them for `tw_feedback` and the subagents in gated repos; this reading inverts the previously pinned "work repo skips session_start peer warnings" test, and a revert, if ever wanted, is confined to the session_start handler and that one test.
- **`tw_feedback` registration is unconditional**: it is claimed by 10 of the 11 shipped subagent allowlists, and children do launch in gated repos. The settled claim that pi-subagents refuses to launch a child whose allowlisted tool is unavailable was verified false against the then-installed pi-subagents 0.34.0 source (the launch path forwarded the allowlist as pi's `--tools` with no availability assertion, and pi silently ignored names that never register), and that correction was itself superseded by the bug ticket `subagent-availability-resync`, verified against the lockfile-declared and now-installed 0.84.0: every plain name in an agent's tools allowlist is a required child tool (path-like entries load extensions instead), and a required tool that never registers fails the child's run at agent start with `requested unavailable child tools`, so the child process starts but the run is marked failed. The cost of a missing peer is the chain's runs, not just the feedback rows: 10 of the 11 shipped allowlists also name `submit_feedback`, a pi-telemetry tool, so with pi-telemetry absent every shipped chain's children fail at agent start. The session-start warning and the docs state this version-pinned shape and carry a re-verify-on-upgrade note.
- **Repo-classification contract unchanged**: `disableOnRepo` regex list, per-repo `taskWorkflow.enable` boolean override, normalization, and the truth table all keep their shape and semantics from `docs/repo-gating.md`.
- **Documentation**: `docs/repo-gating.md` is re-synced to the narrowed behaviour, including the smaller strip set, the three passive tools plus the three skill-creator tools, the `tw_open` restriction (covering the whole manifest), the lockdown condition, and the same known `/help` limitation, now scoped to the 10 skills, plus a subagent-launch section, re-verified and version-pinned by the bug ticket `subagent-availability-resync` (on the lockfile-declared pi-subagents 0.84.0 every plain allowlist name is a required child tool, and a required tool that never registers fails the child's run at agent start; the section says to re-verify on any upgrade) and two known-limitation notes (an unknown non-manifest skill name in a gated repo still errors with the full registry list, and `tw_close`'s idle hint is imprecise where only skill-creator opens). The same correction propagated to the entry point's session-start warning wording, `README.md`, and skill-creator's `references/target-pi.md`; seven doc-content tests pin the resynced narrative. The bug ticket's re-correction then restated the warning and `README.md` to the 0.84.0 shape and added a peer-packages section to `target-pi.md` (which never carried the 0.34.0-era launch claim), re-pinning both peer-warning tests and the launch doc-content test and adding one doc-content test for the README and `target-pi.md` wording.

## Existing abstractions to stand on

- The skill registry tables in the disclosure module, which already partition every workflow phase (name, gate, toolset, conflicts); the manifest belongs beside them.
- The existing gate resolver and its truth table in the repo-gate core module; the classification logic is not touched.
- The prompt-strip and skill-invocation handlers in the extension entry point, which already read a name set; they continue to read a name set, just the manifest's.
- The opener's own refusal machinery (refused-outcome shape with `reason` and `legal_next`), reused for the gated-name refusal, keeps one refusal language; the refusal runs in the execute handler ahead of `validateOpenArgs`, whose throw-based unknown-skill path stays unchanged for non-manifest names.
- The gate-factory test seam (stub extension API capturing tools, handlers, notifications) in the existing test suite; new dual-state tests extend it instead of inventing a second fixture style.
- The static-name diagnostics channel (`SKILL_NAME_DIAGNOSTICS` notified at session start) survives for the package.json read failure, fed by the narrowed `loadSkillNameDiagnostics()` helper that derives no names; the consistency test makes that failure near-impossible anyway.

## Do-not-reimplement

- Do not invent a second keep-list or per-skill metadata flag on top of the manifest; the registry already has the gate/conflict shape, and a second mechanism is what replaced the derivation.
- Do not keep `loadGatedSkillNames` as a fallback path with different names: one list, one source, pinned by the consistency test.
- Do not make the skill-creator script tools default-active in the gated branch to compensate for the disclosure; the restricted `tw_open` is the activation path in both gate states, and a second activation rule is exactly the drift this effort removes.
- Do not copy the write-guard refusal text into a new guard; the existing guard moves behind the new condition as-is.

## Seams

- **Manifest seam**: one exported constant next to the registry, plus the two opener helpers beside it (`openableWhenGated()` and `gatedReason()`); the strip list, the invocation block, and `tw_open`'s restriction all consume it.
- **Registration seam**: the tool-registration loop and `notify_user` registration in the extension entry point branch on gate state; the set of names each state contributes is a pure function of the gate result, and the gate-specific name lists (`GATED_REGISTERED_TOOLS`, `SKILL_CREATOR_TOOL_NAMES`) stay module-private.
- **Opener seam**: `tw_open`'s parameter construction (`buildOpenParameters(gated)`, which narrows the description's enumerated offered list) and the first check of its execute handler (the gated refusal, ahead of `validateOpenArgs`) are where the gated narrowing and refusal land; the gate state arrives through `createTools(gated)`, and the refusal's notify rides the optional `ToolContext.notify` wired in the shared registerTool wrapper; no other tool sees the restriction.
- **Condition seam**: a small "workflow enabled in this repo" predicate (the module-private `workflowEnabled(gate)`) separates the lockdown and `restoreDeclaredSetFromTranscript` from the passive tool registration; the two used to be glued to one boolean.
- **Docs seam**: `docs/repo-gating.md` is the single narrative contract; the CHANGELOG entry happens at ticket close-out, not here.

## Per-ticket contracts

- **gated-skill-manifest exports**: a named constant with the 10 names, plus its consistency rule: the exact 10-name literal pin, every manifest name a `pi.skills` basename, and the registry entries outside the manifest exactly `["skill-creator"]` (the planned "manifest names are exactly the registry workflow skills" was not implementable: three of the ten names own no toolset and therefore have no registry entry). Consumers: the prompt strip, the `/skill:` block, and `tw_open`'s restriction in the next tickets. Verifiable on its own: the consistency test (in `tests/skills.test.ts`) fails on a renamed or added skill.
- **gated-tool-registration exports**: the registration split (passive set + skill-creator tools + `notify_user` in gated repos, full set in ungated repos) and the new "workflow enabled" condition that owns the lockdown and the declared-set replay; the gated session-start early return is gone, so the gate diagnostics and the peer-extension warnings fire in both states. Handed forward to the next ticket (a registered surface, not a code export; the new gate-specific names are module-private): `tw_open` is registered in both states through the normal registerTool surface, so its restriction has a place to live. Verifiable on its own: the dual gate-state factory assertions pass against the stub extension API.
- **tw-open-gated-restriction exports**: a `tw_open` that, in gated repos, offers only non-gated registry entries (the description's enumerated list narrows; `skill` stays a plain string) and refuses every manifest name, with or without a registry entry, using the opener's refused-outcome shape (the refusal is the first check in the execute handler, ahead of `validateOpenArgs`; the notify is best-effort through the optional `ToolContext.notify`; `legal_next` derives from `openableWhenGated()`); plus the disclosure exports `openableWhenGated()` and `gatedReason()`; plus a proof (test) that the open-set derivation cannot derive a workflow skill as open from the passive active set. Verifiable on its own: the stubbed `tw_open` refuses all ten manifest names and opens skill-creator in the gated shape.
- **repo-gating-docs-resync delivers**: a re-synced `docs/repo-gating.md` (strip set, passive tools, `tw_open` restriction over the whole manifest, lockdown condition, re-scoped `/help` limitation, known-limitation notes) and the verified pi-subagents note, which took the correction arm against the then-installed 0.34.0 (no launch-time allowlist check: the launch path forwarded the allowlist as pi's `--tools`, and pi ignored names that never register, so the cost was the feedback row at call time, not the launch), later superseded by the bug ticket `subagent-availability-resync` against the lockfile-declared 0.84.0 (every plain allowlist name is a required child tool, and a required tool that never registers fails the child's run at agent start, so the cost is the chain's runs); the corrected wording propagated to the entry point's session-start warning, `README.md`, and skill-creator's `target-pi.md`, pinned by seven doc-content tests. Verifiable on its own: the doc matches the registered surface that ticket two and three's tests pin.

## Engineering checks handed from planning

- Disclosure soundness when only skill-creator can disclose: resolved as the derivation-proof test inside `tw-open-gated-restriction`; it holds.
- Exact pi-subagents launch-failure shape for unavailable allowlisted tools: resolved twice. `repo-gating-docs-resync` verified the launch-failure premise false against the then-installed 0.34.0 (no launch-time allowlist check; the failure was the feedback row at call time); the bug ticket `subagent-availability-resync` superseded that against the lockfile-declared 0.84.0: every plain allowlist name is a required child tool, and a required tool that never registers fails the child's run at agent start, so the failure is the chain's runs, not just the feedback row. The durable rule, now also in `docs/testing.md`, is that a ticket verifying another package's behaviour pins the version and verifies against the lockfile-declared one; the shipped record carries a re-verify-on-upgrade note.
- The stale gate-factory fixture cleanup: absorbed by `gated-tool-registration` (the stale list renamed to the full surface, the strip tests rebound to the static manifest).
